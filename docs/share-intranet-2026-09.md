# 让 AI Agent 高效读知识库：渐进式披露 + 用完即卸
### opencode-okf-context 行内推广分享（2026-09）

---

## 0. 一页结论

> **Agent 查知识库的常见方式（skill + Python 脚本 grep + 整文件读入）会把读过的内容永久留在上下文里。**
> 实测（200 概念行内风格知识库、20 轮问答会话）：
>
> | 指标 | skill+Python 脚本 | 本插件（渐进+自动卸载） | 差距 |
> |---|---|---|---|
> | 期末上下文 | 244,811 chars（~61K token） | 35,508 chars（~8.9K token） | **6.9x** |
> | 全程累计输入（计费/延迟口径） | ~1.17M token | ~221K token | **5.3x** |
> | 检索延迟（每次查询） | 19ms（起进程+全树扫描） | <1ms（内存元数据） | **20x+** |
> | 磁盘扫描 | 每次查询全量扫描 429K chars | 启动加载一次，之后 0 | — |
>
> 压缩不丢答案：**卸载后正文细节类问题的最终命中率与不压缩持平**（真实 LLM 多轮实测：占位符的重读提示驱动模型 100% 恢复信息，代价仅一次重读）。
>
> 边界（诚实）：检索层快 120x，但**单题一次性问答**场景通用文件工具端到端更快（常驻提示税，见 4.5）——插件的价值在多轮会话累积、检索确定性与压缩抗性。
>
> 一句话：**不是"装得下装不下"的问题，而是每一轮都在为滞留的旧知识重复付费（token/延迟/注意力），且长会话下上下文质量持续劣化——会话拉到 80 问，脚本方式期末 ~211K token 直接顶穿 256K 窗口，插件稳定在 ~29K。**

## 1. 背景：Agent 读知识库的三种现状

行内 Agent（编码助手、运维助手）接知识库的典型姿势：

1. **全量塞**：把整个 wiki / 表说明文档贴进系统提示。40 个概念 ~4 万字符还能忍，知识库到几百概念后直接不可行。
2. **skill + 脚本**（本次对照组）：写一个 skill 引导 Agent 用 Python 脚本 grep 检索、整文件读入。
   问题有三层：
   - **检索粗**：关键词命中多个文件，Agent 通常要连读 2-3 个文件才找对；
   - **整读**：脚本只会 `cat` 全文，哪怕只需要一个定义；
   - **永不释放**：读过的内容永久留在上下文，后续每一轮都重新计费、重新参与注意力。
3. **通用工具乱翻**：Agent 拿 read/grep/glob 自己探索，比脚本更没章法。

这些方式共同的问题：**知识"进入上下文"没有门槛，"离开上下文"没有机制。**

---

## 2. 方案：opencode-okf-context

[OKF（Open Knowledge Format）](https://github.com/GoogleCloudPlatform/knowledge-catalog) 是 Google 开源的知识包格式：每个概念是一个带 YAML frontmatter（`type`/`title`/`description`）的 markdown 文件，目录带 `index.md` 索引。本插件利用这套**原生结构**做两件事：

### 2.1 渐进式披露（三层）

```
L0 清单（常驻系统提示，~2000 字符）
   bundle 列表 + 使用引导
        │ okf_list / okf_search
L1 索引（按需，只含标题+描述）
        │ okf_read
L2 全文（按需，体积大，有生命周期）
```

- `okf_search`：**元数据优先**（title/description/tags），查不到才回退扫正文——绝大多数查询只花几百字符就定位到概念 id；
- `okf_list`：浏览目录索引，只有标题和描述，没有全文；
- `okf_read`：加载需要的那个概念的全文，输出头部带 `<!-- file: ... -->`，Agent 可直接 Read/Edit 磁盘文件。

### 2.2 用完即卸（outbound-only）

- 加载的概念在 N 轮用户消息后（默认 4）自动替换为紧凑占位符（标题+类型+描述，~250 字符）；也可随时 `okf_unload` 手动释放；
- 同概念重复读取自动去重（只留最新全文）；同词重复搜索只留最新结果，陈旧检索结果同样老化（保留最近一次）；
- 滞留内容超阈值时在最后一条用户消息上锚定一行软提醒。
- **关键安全属性：所有替换只发生在"发往 LLM 的途中"，真实会话历史永远不被修改。** 这是纯确定性的字符串处理，零额外 LLM 调用、零外联。

### 2.3 七个工具

`okf_list` / `okf_read` / `okf_search` / `okf_write`（部分更新，只改传入字段）/ `okf_validate`（只读校验+修复命令）/ `okf_unload` / `okf_refs`（引用图谱，影响分析："谁依赖这张表？"）

## 3. 行内落地形态：一套内核，三种入口

| 入口 | 面向 | 能力 |
|---|---|---|
| **opencode 插件** | opencode 用户 | 全套：渐进披露 + **自动卸载/去重/提醒** |
| **`okf` CLI**（随包分发） | 其他 Agent（shell 调用）、人、CI | 渐进披露 + **摄入控制**（`--fields` / `--section` / `--max-chars`）；默认**只读**（`--write` 显式开启） |
| **`okf validate --all`** | CI / 门禁 | 知识库规范性校验，有 error 退出码 1 |

> **为什么 CLI 没有自动卸载？** "重写发往 LLM 的消息"是 opencode 运行时的钩子能力，其他 Agent 平台没有等价物。CLI 的上下文手段是**从源头少读**（`--fields` 只看元数据、`--section` 只读一节、`--max-chars` 截断），且 read 输出明确告诉模型"不要重复读取"。

## 4. 压力测试：skill+Python 脚本 vs 渐进式加载

### 4.1 方法论（先说清楚怎么测的）

- **数据集**：合成行内风格 OKF bundle（200 概念：tables/metrics/glossary/runbooks/reference，正文共 428,809 字符，其中 reference 文档 5.5-9K）；另用仓库自带的 40 概念真实数据集交叉验证。
- **对照组 S0（现实的脚本方式）**：skill 说明常驻上下文 + 真实运行 `python3 baseline_reader.py`（grep 式检索，真实输出字节数）+ 按真实行为读入"目标文件 + 第一个干扰命中"（grep 命中多个文件时 Agent 的典型动作）。**读入内容永久滞留**。
- **对照下界 S0i（脚本的理想极限）**：假设脚本检索永不失误、不产生检索输出、每次恰好只读对的那一个文件——现实做不到，仅用于诚实对比。
- **实验组 S1**：插件渐进披露（search 元数据优先 + read 全文），不启用卸载。
- **实验组 S2**：插件默认配置（渐进披露 + afterTurns=4 自动卸载 + 去重 + 阈值 25000 提醒）。
- **真实性**：所有输出字节均来自真实执行（真实 python 子进程、真实的插件 search/read 输出、真实的出站 transform 逐轮运行）；唯一模拟的是 Agent"读什么"的策略，已在各组明确标注。
- token 估算：英文内容 chars/4；中文约 chars/1.7（对两种方式同向放大，不影响比值）。

### 4.2 结果一：200 概念 × 10 个问题（20 轮会话）

| 策略 | 期末上下文 | 峰值 | 累计输入 | 工具调用 | 检索延迟 |
|---|---|---|---|---|---|
| S0 skill+Python（现实） | 108,947 chars（~27.2K tok） | 108,947 | ~249.5K tok | 30 | 22ms |
| S0i 脚本理想下界 | 29,946 chars（~7.5K tok） | 29,946 | ~76.2K tok | 10 | — |
| S1 插件·不卸载 | 47,846 chars（~12.0K tok） | 47,846 | ~119.2K tok | 20 | — |
| **S2 插件·默认配置** | **22,915 chars（~5.7K tok）** | **22,915** | **~72.9K tok** | **20** | **<1ms** |

每轮上下文轨迹（chars）——第 5 轮起卸载开始生效（S2 与 S1 分叉），第 15 轮起检索结果老化还会让上下文**回落**：

| 轮次 | S0 现实 | S0i 理想 | S1 不卸载 | S2 默认 |
|---|---|---|---|---|
| 1 | 6,379 | 2,459 | 4,262 | 4,262 |
| 5 | 16,404 | 5,953 | 10,337 | 8,319 |
| 10 | 37,438 | 10,923 | 18,346 | 12,882 |
| 15 | 78,393 | 24,083 | 36,403 | **18,861**（回落） |
| 20 | 108,947 | 29,946 | 47,846 | 22,915 |

### 4.3 结果二：会话长度发散（200 概念，10 → 80 个问题）

| 问题数 | S0 现实 | S0i 理想 | S1 不卸载 | **S2 默认** | S2 ÷ S0i |
|---|---|---|---|---|---|
| 10 | 108,947（~27K tok） | 29,946（~7.5K） | 47,846（~12K） | 22,915（~5.7K） | 77% |
| 20 | 244,811（~61K） | 63,232（~15.8K） | 101,776（~25K） | 35,508（~8.9K） | 56% |
| 40 | 480,902（~120K） | 129,167（~32K） | 208,909（~52K） | 61,060（~15K） | 47% |
| 80 | 844,087（**~211K** ⚠️） | 244,719（~61K） | 389,900（~97K） | **114,599（~29K）** | 47% |

三个关键读数：

1. **现实脚本方式在 80 问时期末上下文 ~211K token，已顶穿 256K 窗口的有效容量**（这还没算系统提示和工具 schema）——会话要么被迫触发平台自带的 LLM 压缩（又回到摘要式路线的成本），要么开新会话丢失上下文。S2 稳定在 ~29K token。
2. **三条滞留斜率**（每问新增的常驻字符）：现实脚本 ~11.4K，理想脚本 ~3.1K，插件 ~1.3K。插件的斜率不到理想脚本的一半、现实脚本的 1/9——所以从第 10 问起插件就低于"理想脚本"的期末占用（77%），80 问时只有它的 47%。
3. 累计输入口径下 S0 现实 80 问已达 **~1550 万 token**（每轮全量重发），S2 约 245 万——计费与首 token 延迟同比例受益。

### 4.4 结果三：真实 40 概念数据集交叉验证（10 问题）

| 策略 | 期末上下文 | 累计输入 |
|---|---|---|
| S0 现实 | 50,862 chars（~12.7K tok） | ~140.7K tok |
| S0i 理想 | 9,879 chars（~2.5K tok） | ~27.3K tok |
| **S2 默认** | **20,417 chars（~5.1K tok）** | **~59.8K tok** |

真实数据上趋势一致：期末上下文 **2.5x** 缩减、累计输入 **2.4x** 缩减。

### 4.5 读取效率（微基准 + 真实 Agent 两层）

**微基准**（`benchmark/readeff.ts`，200 概念库，每答一题的平均成本，全部真实执行计时）：

| 路径 | 每问墙钟 | 进入上下文 | 磁盘读取 | 工具调用 |
|---|---|---|---|---|
| skill·现实（搜索+读对+读一个干扰） | 45ms | 9,747 chars | 436KB | 2.8 |
| skill·理想（搜索+只读对） | 33ms | 7,699 chars | 434KB | 2.0 |
| **插件·进程内（opencode 工具）** | **0.37ms** | **3,191 chars** | **0**（启动 36ms 只付一次） | 2.0 |
| 插件·CLI（其他 Agent，无状态） | 142ms | 3,440 chars | 435KB（每命令重扫描） | 2.0 |

检索机制差异一目了然：内存元数据 vs 起进程全树扫描（**120x**），且 skill 每问带进上下文的字符是插件的 **3.1x** 并永久滞留。

**真实 Agent 端到端**（`OKF_EFF_E2E=1 bun test tests/efficiency-e2e.test.ts`，一次性单题问答，插件工具 vs `--pure` 通用文件工具，n=4）：

| 臂 | 墙钟/题 | 工具调用/题 | 工具输出/题 | 答对 |
|---|---|---|---|---|
| 插件（okf_search → okf_read） | 23.8s | 2.3 | 1,768 chars | 4/4 |
| skill（glob/grep/read 自主探索） | **7.8s** | 3.0 | 2,141 chars | 4/4 |

**诚实读数**：单题冷启动场景，通用文件工具端到端**反而快 ~3 倍**——墙钟由 LLM 推理主导，而插件的 L0 清单 + 7 个工具定义常驻系统提示，在 flash 级模型上是每次请求都要付的固定税。同时这批 fixture 的文件名与标题一致，glob 能直达目标文件；真实行内知识库布局没这么规整时，skill 路径的成本会向微基准"现实"行（45ms + 9.7K chars + 全树扫描）回归。

**效率结论**：插件的优势在**多轮会话累积**（4.2/4.3：滞留斜率 1.3K vs 11.4K 字符/问，4-7x）、**检索确定性**（元数据检索不依赖文件名规范）与**压缩抗性**（4.7）；单题一次性问答是它的成本项（常驻提示税）——以一次性问答为主的场景可调小 `maxManifestChars` 或改用 `okf` CLI。

### 4.6 压缩对命中率的影响（两层实测）

"自动卸载会不会把还要用的信息丢掉？"——分两层回答：

**第一层：确定性信息保留率**（`benchmark/hitrate.ts`，真实 transformOutbound 逐轮运行）。对真实数据集的 22 个概念各提取两类事实——元数据类（标题/类型/口径描述）与正文细节类（正文中的具体句子）——在第 1~10 轮探测出站快照中该信息是否仍在：

| 配置 | 元数据类事实保留 | 正文细节类事实保留 |
|---|---|---|
| 不卸载（对照） | 100%（220/220） | 100%（220/220） |
| 默认（卸载 + description 占位符） | **100%**（220/220） | 40%（=仍在上下文内的轮次占比） |
| minimal 占位符 | 40% | 40% |

正文细节的保留率随轮次精确衰减：第 1-4 轮 100% → **第 5 轮起 0%**（afterTurns=4 + 挤出 keepRecent=2，与配置严格吻合）。即：**卸载后，正文细节确实离开了上下文**——这是确定性事实，不是概率。顺带验证了占位符模式的价值：description 模式保住全部元数据类问题，minimal 模式连元数据也丢（所以默认用 description）。

**第二层：真实 LLM 的最终命中率**（`OKF_RELOAD_E2E=1 bun test tests/reload-e2e.test.ts`，真实多轮 opencode 会话，模型 deepseek-v4-flash）。场景：第 1 轮加载概念 X，第 2/3 轮加载另两个概念（把 X 挤出 keepRecent），第 4-6 轮填充轮（X 确定性老化卸载），第 7 轮**中性提问**要求逐字引用 X 正文中含数字的句子（四词窗口精确匹配，猜不出来）：

| 组 | 重读率 | 答对率 | 说明 |
|---|---|---|---|
| 治疗组（默认自动卸载） | **2/2** | **2/2（100%）** | 模型都跟随占位符的重读提示重新 `okf_read` 后逐字答对 |
| 对照组（不卸载） | 0/3 | 3/3（100%） | 全文在上下文，直接答对 |

**结论：压缩没有造成可测的命中率损失**——正文信息虽然离开了上下文（第一层），但占位符的提示可靠地驱动模型在真正需要时恢复它（第二层），最终命中率与不压缩持平；代价是每场景多一次 `okf_read` 调用（~2K 字符，一次性），对比不卸载的永久滞留（每轮都算钱）。样本量小（有效场景 2+3）、可随时复跑，但方向一致且与确定性层的机制解释吻合。

### 4.7 压缩抗性：插件 vs skill（平台 auto-compact 场景）

"平台自动压缩发生时，谁还能找到知识库？"先校准一个概念：插件里**常驻的是 L0 清单**（bundle 列表 + 触发指引 + 工具用法，注入在**系统提示**里，每次请求重建——压缩只摘要消息历史，动不了它）；L1 索引并不常驻，但丢了随时可再拉。skill 的说明文档和加载过的索引都在**消息历史**里，正是压缩的摘要对象。

**确定性层**（`benchmark/compaction.ts`，压缩模型：保留最近 2 轮 + 212 字符主题级摘要，与各平台 auto-compact 行为一致——摘要由用户文本生成，工具输出/路径/命令语法不会进入）：

| 压缩后存活维度 | skill（历史驻留） | 插件（系统提示驻留） |
|---|---|---|
| KB 访问指引（工具/命令名） | **0%** | **100%** |
| bundle 清单（知道知识库存在） | **0%** | **100%** |
| 触发指引（何时该查） | **0%** | **100%** |
| 已加载正文 | 0% | 0%（两臂同——差异在可恢复性） |

**真实 LLM 层**（`OKF_COMPACTION_E2E=1 bun test tests/compaction-e2e.test.ts`，压缩后同题逐字引用测试）：

| 臂 | 配置 | 答对率 | 恢复路径 |
|---|---|---|---|
| A 插件·压缩后 | 插件开，摘要不含 KB 信息 | **3/3** | 清单 → `okf_search`（元数据）→ `okf_read`（单概念），一场景还主动调了 `okf_unload` |
| B skill·被压缩遗忘 | `--pure` 关插件，摘要不含 KB 信息 | 3/3 | `glob`/`grep`/`read` **自主探索**整文件找回 |
| C skill·摘要保留入口 | `--pure`，摘要写明库路径与脚本 | 3/3 | `bash` + `read` |

**诚实结论（含一个被实测推翻的假设）**：我们原假设 B 臂会答崩——实测没有，因为能力强的 Agent 靠通用文件工具能把**项目内的本地知识库**重新探索出来。所以准确率层面：**本地库 + 强 Agent 时两者打平（3/3 vs 3/3）**；插件的结构性优势在另外两处：

1. **恢复路径的代价**：A 走"清单 → 元数据检索 → 单概念读取（用完自动卸载）"；B 走的正是压测里 S0 的整文件探索路径（4-7x 的上下文/成本鸿沟，且读入内容永久滞留）——找回答案的过程本身在烧上下文。
2. **可达性边界**：知识库**不在项目目录内**（行内共享挂载、外部知识源）时，B 的再探索通道根本不存在，而插件的清单让"知识库存在 + 怎么查"成为永久上下文——这是 skill 方案在结构上补不回来的差距。

## 5. 怎么接入（行内）

### 5.1 安装（npm 源）

```bash
# opencode 用户：装插件（工具 + 自动卸载）
opencode plugin opencode-okf-context@latest --global

# 要用 CLI 的人/CI：npm 全局装同一个包（bin 链接，得到 okf 命令）
npm install -g opencode-okf-context
```

> ⚠️ **装插件 ≠ 有 CLI**：`opencode plugin` 只加载插件入口，不执行 npm 的 bin 链接，两者是并列安装。建议锁定同一版本号；`okf version` 与插件清单里的自报版本可互相核对。

### 5.2 知识库格式（OKF 极简版）

```
kb/
  index.md            # okf_version: "0.2" 即被识别为知识包
```

放哪都行：自动扫描项目目录；或 `.opencode/okf.jsonc` / `.okf.jsonc` 显式声明 `bundles`。

### 5.3 给非 opencode 的 Agent 接入

运行 `okf manifest`，把输出的片段贴进该 Agent 的规则文件（AGENTS.md / CLAUDE.md / 系统提示词）即可——它告诉 Agent 有哪些命令、什么时候用、读完不要重复读。

## 6. 安全与合规

- **默认只读**：CLI 的写命令需要 `--write` 显式开启；插件侧 `write.enabled` 可配置关闭。
- **不动真实历史**：卸载/去重/提醒全部发生在发往 LLM 的出站副本上，会话存档完整可审计。
- **零外联、零额外 LLM 调用**：纯本地确定性逻辑；npm 源内网部署，无第三方依赖（yaml 已打进包内）。
- **路径约束**：概念读写限制在 bundle 根目录内，防目录穿越；保留文件（index/log）不可被写工具覆盖。

## 7. 诚实的边界（讲清楚什么时候不需要它）

1. **小知识库 + 短会话**（十几个概念、三五个问题）：任何方式都撑得住，插件收益主要是"少读"而不是"卸载"。压测里 S0i 与 S2 在短会话基本持平就是这个道理——**差距随会话长度和检索失误率放大**。
2. **256K 窗口下"装得下"不等于"答得准"**：本插件的另一半价值是注意力质量（更少的滞留干扰）与每轮延迟/计费，这两项与窗口大小无关。
3. **CLI 没有、也不可能有自动卸载**（平台能力边界）；非 opencode Agent 的上下文手段是摄入控制。
4. **不做的**：LLM 摘要式压缩（对比 DCP 路线，本方案零额外 token 但依赖 OKF 结构）；知识库的创作与校验工具链（社区 `opencode-okf` 包的领域，互补不冲突）。
5. **已实施（本次分享所用构建已包含）**：`okf_search` 输出曾不参与卸载/去重（transform 只跟踪 `okf_read`），是压测暴露的最大滞留泄漏——现已实现**同词重复搜索折叠 + 超期检索结果占位化**（保留最近一次检索），滞留斜率从 ~2.7K 降至 ~1.3K 字符/问，对理想基线的期末占用优势从 ~10% 提升到 53%（80 问时仅为其 47%）。

## 8. FAQ

**Q：为什么不直接把知识库全塞进系统提示？**
A：40 概念 ≈ 4 万字符还能忍；几百概念后不可行，而且塞进去的内容每一轮都参与计费和注意力，和脚本方式同病。

**Q：自动卸载会不会把还要用的内容卸掉，导致重读循环？**
A：占位符措辞明确"例行上下文管理，无需动作，确有需要再重读"（防重读循环是 v0.1.7 专项修过的）；`keepRecent`（默认 2）保护最近读取，`protectedConcepts` 保护全程核心文档；256K 调优后默认 4 轮才卸，进一步降低误卸。

**Q：知识库怎么维护？**
A：就是 markdown 文件，git 管理；Agent 自己可以用 `okf_write`（部分更新）维护，人也可以直接编辑；`okf validate --all` 进 CI 把关规范性（type 缺失、断链、缺 log）。

**Q：和 DCP（上下文剪枝插件）什么关系？**
A：互补。DCP 用 LLM 摘要压缩任意内容（通用但有额外 token 成本）；本方案用 OKF 结构做确定性披露/卸载（零额外 token，但要求知识以 OKF 组织）。两者可以并存。
